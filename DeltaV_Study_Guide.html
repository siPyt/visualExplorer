Chapter 1: The Three Equipment Tiers & The Module Scan Heartbeat

1.1 Why DeltaV Splits Control Into Three Layers (Unit Phase → EM → CM)

If you tried to put batch recipe steps, tank coordination math, safety interlocks, valve limit-switch timers, and raw 4–20 mA sensor scaling inside one giant diagram, every module in the plant would look like an unreadable spiderweb. DeltaV prevents that by dividing responsibility strictly across three tiers:

DeltaV Tier Plain-English Role What It Owns (Concrete Plant Example: Solvent Mix Tank)
Unit Phase
(ISA-88: EPH)		 The Recipe Boss Terminology note: ISA-88 calls this an Equipment Phase (EPH); DeltaV Explorer calls it a Phase Class / Unit Phase containing one SFC per composite state (RUN_LOGIC, HOLD_LOGIC, RESTART_LOGIC, STOP_LOGIC, ABORT_LOGIC, plus FAIL_MONITOR). It acquires EM_TANK_CHARGE, writes A_COMMAND := 'em_charge:CHARGE' and RECIPE_WT := 500.0, and waits until A_PV = 'em_charge:CHARGE'.
EM
Equipment Module		 The Team Coordinator Groups related valves, scales, pumps, and motors into one coordinated process task—such as EM_TANK_CHARGE (tank addition) or EM_XFER_HDR (manifold routing). Driven by standard parameters A_COMMAND (with mandatory 255 = Idle), A_TARGET (executing), and A_PV (completed without error). An EM almost never wires directly to physical I/O cards.
CM

1.2 Module Scan Rate, #1 → #2 → #3 Execution Order & Dashed Feedback Wires

Every DeltaV module is assigned a Scan Rate (for Equipment Modules, typically 500 ms or 1 second). Once every heartbeat, the controller wakes up the module, reads incoming parameter references, executes its function blocks, and publishes outgoing writes.

Real-Plant Engineering Trap: Screen Position Means NOTHING — Watch for Dashed Feedback Wires!
In Control Studio Function Block Diagrams, placing a block higher or farther left on the screen does not make it execute first. DeltaV solves FBD blocks strictly according to the Execution Order badge (#1, #2, #3) in the bottom-right corner of each block:
  • Correct Order (Solid Wire = Same Scan): Transfer Switch XFR1 (#1) → Remaining Mass Calculator CALC1 (#2) → Cutoff Condition CND3 (#3). All three solve in the same millisecond pass of the scan.
  • Reversed Order Mistake (Dashed Feedback Wire = Next Scan!): Per DeltaV Configuration (p. 368), whenever a wire's source block has a higher execution number than its destination block (e.g., #2 → #1), Control Studio draws that connection as a DASHED FEEDBACK WIRE because the value will not arrive until the next scan! On a 1-second scan class with solvent flowing at 10 kg/sec, a backward execution order injects 10 kg of dead-time overshoot on every batch!
  • Why PRECLOSE_LEAD Exists: Because DeltaV EMs commonly scan at 500 ms or 1 s—and physical pneumatic block valves take 1–3 seconds to stroke shut—you command the feed valve closed early by PRECLOSE_LEAD (e.g., 15.0 kg before target) to compensate for both actuator stroke time and scan latency.

Chapter 2: Separating "1 Outer Algorithm" from "4 Inner Patterns"

2.1 Clearing Up the Biggest Point of Confusion: Most of an EM Does NOT Step!

When engineers first read descriptions of an Equipment Module—"In Step 10 open the valve, in Step 20 trim and close, in Step 30 start the agitator"—it sounds as if the entire Equipment Module is a sequence of SFC steps. It is not.

Almost every Equipment Module is built out of four cooperating functional jobs ("Patterns"), and only Pattern 1 steps through time. Patterns 2, 3, and 4 have zero steps—they run continuously on every single Scan like permanent hardwiring:

Zone Inside the EM Steps Like an SFC? How It Actually Executes Inside the Controller
Pattern 1: Command, State & Step Flow YES (In Command EMs!) In a Command-Driven EM (EM_TANK_CHARGE), walks sequentially through time (S0_IDLE → S10 → S20 → S30); in a State-Driven EM (EM_XFER_HDR), uses an Items × States table.
Pattern 2: Permissives & Interlocks NO — Always On Watches High-High level and scale health (.ST) on every single Scan. If the scale fails mid-charge, Pattern 2 slams the valve shut immediately without waiting for an SFC transition!
Pattern 3: Mode & Setpoint Routing NO — Always On Continuously selects active target weight (XFR1 Transfer block), computes net & remaining mass (CALC1), and pushes CAS mode requests every Scan.
Pattern 4: CM Command & Feedback NO — Always On Carries commands down to valve/motor CMs (CAS_SP → DC1/CAS_IN_D) and brings physical limit-switch proof (DC1/PV_D → PV) back up every Scan.

Mental Picture: Think of Pattern 1 as the orchestra conductor turning pages of sheet music, while Patterns 2, 3, and 4 are the circuit breakers, mixer board, and speaker cables that stay energized the entire concert.

2.2 "4 Core Algorithms" vs. "4 Patterns" — The House Floor Plan vs. The Rooms Inside

  • Algorithms (Official DeltaV Menu Setting — Pick ONE): The outer container template you select from a dropdown in DeltaV Explorer when creating the Equipment Module.
  • Patterns (The 4 Jobs Living Together Inside That 1 Algorithm): Your 1 chosen Algorithm container can hold all 4 Patterns working together at the same time (like EM_TANK_CHARGE, which combines a Command SFC with continuous FBD blocks). A tiny EM might skip one it doesn't need (an FBD-only EM has zero Pattern 1 steps; a simple State-Driven header needs no analog Pattern 3 setpoint math).
Core EM Algorithm Best Plant Use Case How Control Studio Actually Structures It (Verified vs. Emerson Docs)
1. Command-Driven
(EM_TANK_CHARGE)		 Timed multi-stage equipment tasks (charging, heating, CIP cycles). Hierarchy lists COMMAND_00001, COMMAND_00002, … — each a true multi-step SFC driven by Named Set A_COMMAND (with mandatory 255 = Idle). When the SFC reaches its Termination bar without error, A_PV updates from Idle to the command name (7009 pp. 440, 462).
2. State-Driven
(EM_XFER_HDR)		 Multi-valve headers, manifolds, & routing alignments. Configured as an Items × States Table (NO SFCs!): Per 7016 p. 140, Control Studio opens an Items | States grid. Each Item row defines a module-level Write parameter path (e.g., CM_HDR_XV102/CAS_SP.CV) and Readback parameter path (CM_HDR_XV102/PV.CV). Also driven by A_COMMAND (255 = Idle); A_PV confirms the state once all readbacks match!
3. Function Block Diagram (FBD) Continuous coordination, ratio/split routing, interlock hubs. Pure left-to-right wire sheet of function blocks (CND, ACT, CALC, XFR) solved every Scan with zero SFC charts or state tables.
4. Sequential Function Chart (SFC) Simple standalone single-sequence helpers. One standalone step-by-step SFC sequence for the whole module instead of separate per-command sub-charts.
DeltaV Explorer Menu Heads-Up: Why You'll See 7 Choices in the Dropdown
When creating an Equipment Module Class in DeltaV Explorer, the Algorithm dropdown displays 7 items (7009 p. 436): the 4 core algorithms above plus 3 phase-hybrid options (Phase Algorithm, Phase with command-driven run logic, and Phase with state-driven run logic). Focus on the core 4 first—Command-Driven and State-Driven power the vast majority of plant Equipment Modules.

2.3 Deep Dive: Which of the 4 Patterns Each EM Algorithm Actually Uses

Yes — both Command-Driven and State-Driven Equipment Modules can hold all four patterns, because Control Studio gives both algorithms the same continuous Function Block Diagram (FBD) workspace (CND, ACT, CALC, XFR) alongside their command or state logic. In real plants, however, Command-Driven EMs usually use all 4 patterns (occasionally 3), while State-Driven EMs usually only use 2 or 3:

Pattern Inside the EM 1. Command-Driven EM (Usually 4, drops to 3) 2. State-Driven EM (Usually 2 or 3)
Pattern 1: Command / State Flow Always used — Multi-step SFC per command (S0_IDLE → S10 → S20 → S30 → Termination). Always used — No graphical SFC! Uses a Named Set Items × States table where A_COMMAND snaps all written cells in a column at once.
Pattern 2: Permissives & Interlocks Almost always used — Pre-start CND gates plus every-Scan safety trips and health watchdogs feeding the Phase's FAIL_MONITOR. Usually used (often lighter) — Lives on the FBD sheet: checks valve health/modes (.ST >= GOOD, MODE.ACTUAL) or forces a safe Close state on a tank trip; minimal on simple headers.
Pattern 3: Mode & Setpoint Routing Used when numbers are involved — XFR / CALC setpoint math plus CAS mode requests. Skipped on pure on/off discrete sequences. Usually skipped on FBD — Discrete valve manifolds have no weight/flow math; MODE.TARGET writes (like = Cascade/ or = Auto/) fold straight into rows of the State Table!
Pattern 4: CM Command & Feedback Always used — Writes module-level CAS_SP.CV (→ DC1/CAS_IN_D) and waits on PV.CV (DC1/PV_D) feedback before advancing steps. Always used (built into table!) — Each row pairs a Write path (CAS_SP.CV) with a Readback path (PV.CV) to confirm A_PV automatically.
  • Why Command-Driven EMs Usually Use All 4 (and Drop to 3 Without Analog Math): Because a Command-Driven EM coordinates timed stages (such as charging 500 kg of solvent in EM_TANK_CHARGE), Patterns 1 (multi-step SFC), 2 (pre-start permissives + every-Scan interlocks/watchdogs), and 4 (CAS_SP/PV CM handshakes) are virtually guaranteed. It uses all 4 whenever numeric targets are routed (XFR1 choosing Recipe vs. Local weight + CALC1 computing remaining mass), and drops to 3 on pure on/off sequences—for example, a dust-collector startup EM that opens an isolation damper, waits for PV.CV = OPEN, delays 3 seconds, and starts a blower motor with zero numeric setpoints.
  • Why State-Driven EMs Usually Use 2 or 3 Patterns: A State-Driven EM snaps equipment into an instant lineup (such as a manifold or 2-stage fill valve). Its Core 2 (Patterns 1 and 4) are always present right inside the Items × States table. Adding every-Scan FBD health checks (catching a valve left in AUTO, OS, or Bad .ST) and a safe-close trip brings it to 3 patterns. Pattern 3's FBD analog routing is usually absent because discrete valves only need MODE.TARGET rows inside the table; you only see numeric Pattern 3 logic in a State-Driven EM when states also push preset analog outputs (e.g., a jacket header writing 0%, 40%, or 100% to a control valve).

2.4 Visual Key: What Control Studio Actually Draws On-Line & Off-Line

  1. Function Block Stencils & Pin Reality (FBR pp. 179, 400, 413, 453): Rectangular box with block class above, header bar with tag (CND1), hollow square pins (□), and bottom-right execution badge (#1, #2). Know these exact pin layouts cold:
    • CND (Condition): Has OUT_D output pin ONLY (zero input pins!). Operands are read inside its expression; sets OUT_D = True after staying True for TIME_DURATION seconds.
    • ACT (Action): Has IN_D input pin ONLY (zero output pins!). Evaluates its := assignment expression every scan while IN_D is True, writing directly to external/internal references.
    • XFR (Transfer): DeltaV's real 2-input switch (there is no "BSEL" block in DeltaV!). Pins: IN_1 (selected when SELECTOR = False/0), IN_2 (selected when SELECTOR = True/1), SELECTOR, and OUT.
    • CALC (Calculation/Logic): Pins IN1..IN16 and OUT1..OUT16 (no underscores).
  2. Rectangular Parameter Reference Boxes — Left-In / Right-Out Flow (PDS p. 1): Control Studio draws external and module-level parameters on the Main Diagram (also called the Diagram View or FBD Sheet—your working "canvas") as rectangular boxes with a tiny hollow square pin (□).
    • Left Side = Inputs Coming INTO the Diagram: The hollow square pin sits on the right edge ([ Parameter □ ] ───►), feeding live values from other modules (CM_TANK_WT/AI1/OUT) or module parameters (^/RECIPE_WT.CV) into the function blocks.
    • Right Side = Outputs LEAVING the Diagram: The hollow square pin sits on the left edge (───► [ □ Parameter ]), sending calculated results out of the function blocks to module parameters read by the SFC (^/PERM_READY.CV, ^/VALVE_SHUT_OK.CV) or out to child Control Modules (CM_FEED_XV/DC1/MODE.TARGET).
    • Purple Dashed Lines vs. Solid Green / Black Arrows: Both connect to the exact same Parameter Reference boxes! Solid arrows are real hardwired FBD connections to actual block pins (such as XFR1/IN_2, CALC1/IN2, ACT2/IN_D, or CND1/OUT_D): in real Control Studio On-Line, non-zero wires appear bold black and zero/False wires appear thin black (Visual Explorer tints active bold wires green and tripped wires red as a study aid). Purple dashed lines (no arrowhead) into CND or out of ACT are Visual Explorer learning-only pointers—real Control Studio draws no wire there because CND has zero input pins and ACT has zero output pins, while neutral gray dotted/dashed lines remain reserved strictly for real DeltaV feedback wires!
  3. Solid vs. Bold vs. Dashed Wires (CONFIG p. 368 — Critical!): In DeltaV, solid vs. dashed does NOT mean analog vs. discrete! All normal forward wires are solid; On-Line, a wire turns Bold when carrying a non-zero value, and a wire is drawn Dashed only when it is a feedback wire (source block executes after destination block → arrives next scan).
  4. On-Line Status Icons (CONFIG p. 368, PDS p. 3): White value boxes sit beside pins On-Line. A red ✕ marks Bad status (.ST <= 63), a blue ? marks Uncertain status (64..127), and a yellow highlighted ? indicates non-zero BLOCK_ERR.
  5. SFC Elements & Action Qualifiers (7009-8 pp. 4–24, PDS p. 5): Double-bordered Initial Step (S0_IDLE), bright green border on the active step On-Line, elapsed seconds printed under every step, Transition cross (┼) with True / False underneath, and a Termination bar (═╧═) at the bottom. Key qualifiers: [P] (Pulse — runs on first scan of the step only) and [N] (Non-stored — runs every scan while active; in DeltaV, [N] := assignments keep their written value after the step ends!).
Real-Plant Sighting: Why You See Unwired Parameter Boxes on the Left Side of Live Diagrams

Because CND and ACT expressions can fetch external paths like '//CM_FEED_XV/PV.CV' directly without any wire or diagram box, a real Control Studio sheet will often show a CND block with nothing wired to its left—that block is not disconnected (just double-click it to read its expression). Conversely, in real plants you will also see rectangular Parameter Reference boxes parked along the left side of the Main Diagram with no wires coming off them. That is completely intentional—and stems from three native DeltaV practices (7017 pp. 243–244):

  • 1. Module-Level Internal Reference Shortcuts (e.g., MODE → DC1/MODE): Because MODE has no wireable pin on a DC or PID block, engineers drop an Input Parameter named MODE onto the left side of a Control Module as an Internal Reference pointing to DC1/MODE (or PID1/MODE) with zero wires. That exposes MODE cleanly at the module level so State-Driven EM tables (7016 p. 140) and faceplates can access it.
  • 2. Module Variables & Recipe Inputs Used in Expressions: Parameters such as RECIPE_WT, START_WT, or PRECLOSE_LEAD are dropped onto the diagram so they exist on the module interface for upstream Phases/operators and display live On-Line value boxes right on the sheet—even though only SFC steps, CNDs, or ACTs read/write them via expressions.
  • 3. External Reference Aliases: An unwired External Reference box lets multiple local expressions or DeltaV Operate graphics share one clean local parameter name instead of repeating a long '//...' path.

2-Second Plant Check: Double-click any unwired left-side box and check its Parameter Type—Internal Reference = shortcut to an internal block parameter; External Reference = pointer to another module; Floating Point / Boolean / Named Set = module variable read or written by expressions/SFCs.

Chapter 3: Modes (DC AUTO vs. CAS), Status (>= GOOD), ACT/CND & Syntax

3.1 Operating Modes — And the Critical DC Block Rule (AUTO & CAS Only!)

In general across DeltaV function blocks (FBR pp. 30–35), the platform defines eight modes: OOS (Out of Service), IMan (Initialization Manual), LO (Local Override), Man (Manual), Auto (Automatic), Cas (Cascade), RCas, and ROut. (IMan and LO are automatic override states, never selectable targets.) However, not every block supports MAN!

Critical Plant Discovery (FBR pp. 419, 427 & 7016 p. 40): Discrete DC Blocks Do NOT Have MAN Mode!
While analog/output blocks like PID, AO, and DO use MAN for operator control, a discrete DC (Device Control) block inside a valve or motor CM (CM_FEED_XV/DC1, CM_AGIT_MTR/DC1) supports ONLY Auto and Cas as selectable target modes:
  • CAS (Cascade — Automated EM Control): DC1 copies the upstream EM's command on CAS_IN_D (wired from module parameter CAS_SP) straight into SP_D.
  • AUTO (Operator Control on a DC Block!): Returning a DC block to AUTO gives control of SP_D (OPEN / CLOSE) directly to the human operator on the faceplate—and completely ignores CAS_IN_D from the EM!
  • LO (Local Override) & OOS (Out of Service): If SHUTDOWN_D=1, INTERLOCK_D=0, TRK_IN_D=1, or PERMISSIVE_D=0 in Passive, DC1/MODE.ACTUAL automatically drops to LO. Placing a block in OOS locks it out and marks outputs Bad: Out of Service (Red ✕).

3.2 Three Platform Realities That Catch Engineers on Live DeltaV Sheets

Reality 1: Always Write MODE.TARGET, Always Check MODE.ACTUAL!
Pattern 3's ACT2 writes '//CM_FEED_XV/DC1/MODE.TARGET' := CAS;. However, if an operator puts CM_FEED_XV/DC1 into AUTO on its faceplate—or a valve interlock forces DC1 into LO—MODE.ACTUAL becomes AUTO or LO even if an earlier action wrote CAS to MODE.TARGET! Pattern 2's permissive (CND1) must test '//CM_FEED_XV/DC1/MODE.ACTUAL' = CAS.
Reality 2: Status (.ST) Has TWO Traps — Always Use >= GOOD and Propagate CALC Status!
Every connection carries Current Value (.CV) + Status (.ST). Memorize two verified rules from DeltaV Configuration (p. 81):
  • Trap A (>= GOOD vs. = GOOD): Status integers run 0..63 = BAD, 64..127 = UNC, 128..191 = GoodNonCascade (keyword GOOD), and 192..255 = GoodCascade! Writing .ST = GOOD fails on healthy cascade signals—always write '//CM_TANK_WT/AI1/OUT.ST' >= GOOD for healthy and <= BAD for Bad!
  • Trap B (CALC Outputs Default to GOOD!): Unlike AI or PID, a CALC block's OUT1.ST stays GOOD (128) even when IN2.ST is BAD—unless you explicitly write 'OUT1.ST' := 'IN2.ST'; inside the CALC expression!
Reality 3: How ACT Blocks & SFC [N] Assignments Actually Execute
Per FBR p. 400 and 7009-8 p. 12: an ACT block evaluates its := assignment every scan while IN_D is True (not just once!), and an SFC [N] action evaluates every scan while its step is active. When IN_D goes False (or the SFC step ends), the written parameter retains its last value until another expression writes a new value—so S20_TRIM_CLOSE, HOLD_LOGIC, and ABORT_LOGIC must explicitly write 'vlvnc-sp:CLOSE'!

Chapter 5: Phase Hold, Restart, Abort & The Golden Tare Math

5.1 Where Hold/Restart Live in DeltaV — And How Bad Restart Logic Overfills Tanks

Important Architecture Fact (7016 pp. 70, 202): In DeltaV Batch, Hold, Restart, Stop, and Abort are Unit Phase composite states—not standard Equipment Module states! A Unit Phase contains separate SFCs for RUN_LOGIC, HOLD_LOGIC, RESTART_LOGIC, STOP_LOGIC, and ABORT_LOGIC, plus FAIL_MONITOR (any non-zero failure automatically sends the Phase to Holding). When HOLD_LOGIC pauses or re-commands EM_TANK_CHARGE, your tare math must survive that interruption intact!

In almost every batch plant, CM_TANK_WT measures total gross vessel weight (vessel heel + previous ingredients). If the tank starts with a 100.0 kg heel and the recipe adds 500.0 kg, stopping at 500.0 kg gross would short-charge the batch by 100 kg:

(* Executed ONCE via [P] Pulse on S10_CHARGE_OPEN — NEVER inside RESTART_LOGIC! *) '^/START_WT.CV' := '//CM_TANK_WT/AI1/OUT.CV'; (* Locks at 100.0 kg *) (* Inside CALC1 (#2) — solved every Scan *) NET_WT := 'IN2.CV' - 'IN3.CV'; 'OUT1.CV' := 'IN1.CV' - NET_WT; 'OUT1.ST' := 'IN2.ST'; (* Propagate Bad status! *)

Proof by Numbers (Why You NEVER Re-Tare on Restart): Suppose you start at 100 kg heel (START_WT.CV = 100) targeting 500 kg net addition (600 kg final gross). At 300 kg gross (200 kg added), the Phase goes to Hold to check a pump strainer, then executes Restart:

  • Correct DeltaV Design (Tare Preserved): START_WT.CV stays at 100 kg. On Restart, NET_WT = 300 - 100 = 200 kg, so the EM adds only the remaining 300 kg and stops cleanly at 600 kg.
  • Broken Design (Re-Taring During Restart): Overwrites START_WT.CV := 300 kg! Now NET_WT resets to 0 kg, so the EM pumps a brand-new 500 kg on top of 300 kg—slamming the vessel to 800 kg (200 kg overfill!).

7.3 How the 4 Patterns Fit Inside a State-Driven EM (The "3-in-1 Table" Insight)

Once you see the real Items × States editor, State-Driven EMs become effortless to read—because DeltaV's State Table bundles three of the four EM patterns into a single grid, leaving only safety/health checks on the FBD sheet:

EM Pattern (Job) How Command-Driven Does It (EM_TANK_CHARGE) How State-Driven Does It (Course 7016)
1. State / Step Coordination Multi-step SFC chart (Steps + Transitions + Termination). No SFC! A_COMMAND selects a column in the State Values Table and writes every checked row at once.
2. Permissives & Interlocks CND / ACT / CALC blocks on the FBD sheet (surfacing faults to the owning Phase's FAIL_MONITOR). Lives on the FBD sheet — every-Scan CND/CALC health watchdogs (catching Bad .ST or wrong CM modes) + safety interlocks forcing A_COMMAND := Close.
3. Mode & Value Routing XFR / CALC / ACT blocks on the FBD sheet. Folded straight into rows of the State Table (such as MODE.TARGET rows setting = Cascade/ or = Auto/, or states pushing preset analog setpoints).
4. CM Command & Feedback Explicit CAS_SP.CV writes in SFC actions paired with manual PV.CV CND checks. Built automatically into each row's Write Path (CAS_SP.CV) and Readback Path (PV.CV), confirming match status on A_PV!
Plain-English Breakdown: What Does "MODE.TARGET Writes Fold Into Rows of the State Table" Mean?

Think of a valve's MODE as who is holding the steering wheel: CAS (Cascade) means the Equipment Module holds the steering wheel (obeying CAS_SP.CV), while AUTO means the Operator holds the steering wheel (ignoring CAS_SP.CV). Switching who holds the wheel is Pattern 3 (Mode Routing).

  • Command-Driven way (EM_TANK_CHARGE): You must write explicit code inside an SFC action or ACT block ('//CM_FEED_XV/MODE.TARGET' := CAS;) and separately build a CND or transition check to verify MODE.ACTUAL = CAS.
  • State-Driven way ("folded into rows"): You write zero ACT blocks and zero SFC actions for mode switching. Instead, you simply add a regular row to the Items × States table whose Write path is MODE.TARGET and Readback path is MODE.ACTUAL (such as BULK_MODE right below the BULK_CMD row).
  • Decoding Control Studio's = Cascade/ and = Auto/ cell syntax (7016 p. 140): The leading = means "write this value to the Write path and verify the Readback path matches it before confirming A_PV," while Cascade/ and Auto/ are how Control Studio displays mode values (CAS / AUTO) inside a State Table cell.
  • Why this is so powerful on the plant floor: In Bulk (3), row BULK_MODE writes = Cascade/ and automatically checks MODE.ACTUAL = CAS—if an operator leaves the valve in AUTO, that row fails readback and drops A_PV to Idle (255) with zero extra FBD logic! Conversely, in Auto Mode (4), row BULK_MODE writes = Auto/ while BULK_CMD stays (not written), handing the steering wheel back to the operator without moving or slamming the valve.
Native Verification Note: Where Does FAIL_MONITOR Actually Live?
In Course 7016 (pp. 70, 202), FAIL_MONITOR is a native composite block automatically built into Unit Phases (when non-zero, it sends the Phase to Holding). Inside an Equipment Module, engineers build equivalent every-Scan watchdog blocks (CND / CALC) directly on the EM's FBD sheet to flag a stuck valve, wrong mode, or Bad .ST—and the upstream Unit Phase's FAIL_MONITOR monitors that EM alarm!

Chapter 8: Analog Control Modules, PID Loops & Back-Calculation (FIC_101)

In continuous (non-batch) plants, 80%+ of the Control Studio sheets you open will be Analog Regulatory Control Modules—flow, pressure, level, and temperature loops built around AI → PID → AO. Unlike discrete DC valves (which snap OPEN or CLOSE), analog loops throttle continuously from 0% to 100% and rely on a backward feedback wire—BKCAL_OUT → BKCAL_IN—to prevent windup and keep mode transitions 100% bumpless.

8.3 BKCAL_OUT → BKCAL_IN: Why That Gray Dotted Feedback Wire Saves Your Plant

Imagine your flow control valve (AO1) is stuck or saturated at 100% open while flow is still below setpoint (PV = 60, SP = 80). Without back-calculation, a naive PID's integral ("reset") term would keep winding up to +500% inside memory; later, when flow rises above 80 gpm, the valve would stay slammed wide open for minutes waiting for the wound-up integral to unwind!

DeltaV solves both integral windup and bumpless transfer with one wire—AO1/BKCAL_OUT looped back to PID1/BKCAL_IN (drawn gray dotted because #3 feeds back to #2 for the next scan!):

  1. GoodCascade: Non-Limited: Valve is freely moving in CAS → PID1 integrates normally in AUTO.
  2. GoodCascade: Limited High (or Limited Low): AO1 hit OUT_HI_LIM (100%) or OUT_LO_LIM (0%). PID1 freezes integral accumulation in the limited direction (FBR p. 239)—zero reset windup!
  3. GoodCascade: Not Invited (Init Request): An operator switched AO1 to MAN (say 42%). AO1 sends 42% + Not Invited backwards on BKCAL_OUT → PID1 immediately drops to IMan and forces PID1/OUT := 42%! The instant the operator returns AO1 to CAS, PID1 resumes AUTO from 42% with zero valve bump!
  4. Bad: Out of Service: AO1 is in OOS or faulted → PID1 holds in IMan until the downstream block is healthy again.

Chapter 9: Cascade Control & CTLSL Override Control (CASCADE_201)

9.1 Master → Slave Cascade & The Double BKCAL Chain (TIC_201 → FIC_201 → AO_VLV)

In a reactor or heat exchanger, temperature changes slowly (minutes), while steam header pressure can fluctuate in seconds. Rather than letting the slow Temperature PID directly wrestle the steam valve, engineers nest a fast Slave Flow PID (PID_FIC) inside a slow Master Temperature PID (PID_TIC):

  • Forward Path (Left → Right): Master PID_TIC (#2, AUTO) outputs a desired Steam Flow Setpoint (gpm) into Slave PID_FIC (#3, CAS)/CAS_IN, which drives AO_VLV (#4, CAS)/CAS_IN. If steam supply pressure suddenly dips, the fast Slave FIC opens the valve in 2 seconds before reactor temperature ever budges!
  • Backward Path (Double Gray Dotted BKCAL Feedback Chain): AO_VLV/BKCAL_OUT (#4 → #3) feeds PID_FIC/BKCAL_IN, and PID_FIC/BKCAL_OUT (#3 → #2) feeds PID_TIC/BKCAL_IN!
    • Operator puts Slave FIC in AUTO or MAN: Slave sends Not Invited up #3 → #2 → Master TIC immediately drops to IMan and tracks the Slave's actual flow setpoint/PV bumplessly!
    • Operator puts AO_VLV in MAN: Not Invited ripples backwards through both gray dotted wires → BOTH Slave FIC AND Master TIC drop to IMan!
    • Valve saturates at 100%: Limited High ripples up both gray dotted wires → integral windup freezes on both PIDs!
    • Pro Tip (Dynamic Reset Limit, FBR p. 238): Checking FRSIPID_OPTS: Dynamic Reset Limit on Master PID_TIC feeds Slave FIC's actual flow PV directly into Master's reset network—preventing windup even if the steam valve is wide open or a manual isolation valve upstream is half-shut!

9.2 Override Control Using DeltaV's CTLSL (Control Selector — FBR pp. 185–189)

Suppose a pump normally runs on Flow Control (PID_FLOW), but if discharge pressure climbs above 8.5 bar (say a downstream filter plugs up), you want a High-Pressure Override Controller (PID_HI_PRESS) to smoothly take over the control valve and pinch flow back before bursting a line—without tripping the whole plant!

  • Real DeltaV Block Name: CTLSL (Control Selector) — accepts up to 3 PID outputs on SEL_1, SEL_2, SEL_3 plus BKCAL_IN from AO_VLV, and picks the winner using SEL_TYPE (LOW, HIGH, or MIDDLE).
  • Why You MUST Use CTLSL (and NOT XFR or CALC) for PID Overrides: CTLSL has three dedicated back-calculation outputs: BKCAL_SEL1, BKCAL_SEL2, and BKCAL_SEL3! While PID_FLOW is winning LOW-select in normal operation, CTLSL sends the winning output + Limited High back on BKCAL_SEL2 so PID_HI_PRESS stays primed right at the current valve position with zero windup. The instant pressure crosses 8.5 bar, PID_HI_PRESS drops below PID_FLOW and takes over smoothly on the very next scan while BKCAL_SEL1 clamps PID_FLOW!
  • 2:00 AM Plant Gotcha (FBR p. 187): CTLSL supports 4 modes (OOS, IMan, Man, Auto). If ANY connected SEL_1, SEL_2, or SEL_3 input goes Bad while CTLSL is in Auto, CTLSL automatically sheds its actual mode to Man (holding the valve steady until the sensor recovers, when it resumes Auto)!

10.2 Choosing the Right Selector Block: XFR vs. ISEL vs. CTLSL

Real plant sheets use three different selector blocks—never confuse them:

  • XFR (Transfer — FBR p. 453): 2 analog inputs (IN_1, IN_2) + discrete SELECTOR + BAL_TIME linear ramp. Best for bumplessly switching between 2 setpoints or 2 sensors using a Boolean flag.
  • ISEL (Input Selector — FBR pp. 201–202): Up to 4 redundant sensors (IN_1..IN_4) with individual DISABLE_1..DISABLE_4 bypasses, manual OP_SELECT (1–4, or 0 for auto), and SELECT_TYPE = MAX, MIN, MID (median of 3!), FIRST_GOOD, or AVG. Automatically ignores any sensor whose status is Bad or DISABLE = True! Ideal for 2-out-of-3 redundant reactor thermocouples or level transmitters!
  • CTLSL (Control Selector — FBR p. 185): Up to 3 PID outputs (SEL_1..SEL_3) with dedicated BKCAL_SEL1..3 anti-windup feedback wires. Always use CTLSL (never ISEL or XFR) when selecting between competing PID controllers!

FB-1. XFR — Transfer Function Block (e.g., XFR1 • FBR pp. 453–455)

Plain-English Job: A bumpless 2-input analog selector switch with a built-in linear ramp timer. (Remember: there is no "BSEL" block in Emerson DeltaV—XFR is the real block used to choose between two analog sources such as Recipe Weight vs. Local Weight, or Sensor A vs. Sensor B!)

Figure F1: Transfer (XFR1) Block Internals — Note exact underscore pin names (IN_1, IN_2), BAL_TIME linear ramp, and automatic worse-status propagation from BOTH the selected input and SELECTOR.
  • Exact Selection Logic: SELECTOR = False (0) routes IN_1 to OUT; SELECTOR = True (1) routes IN_2 to OUT.
  • BAL_TIME (Balance / Ramp Time, seconds): Controls how smoothly OUT transitions when SELECTOR flips. With BAL_TIME = 0 (used on XFR1 for discrete batch target weights), OUT snaps instantaneously. With BAL_TIME > 0 (e.g., 15 s on a flow setpoint or temperature sensor switchover), XFR ramps linearly over 15 seconds so you don't shock a downstream PID loop!
  • 2:00 AM Plant Gotcha (Status Propagation): Per FBR p. 454, OUT.ST automatically becomes the worse status of the selected input AND SELECTOR. If SELECTOR comes from a broken upstream block (Bad status), XFR1/OUT.ST turns Bad (Red ✕) even though IN_1 and IN_2 are both healthy! Also notice the spelling trap: XFR uses underscores (IN_1, IN_2), while CALC does not (IN1, IN2).

FB-2. CALC — Calculation / Logic Block (e.g., CALC1 • FBR pp. 179–182)

  • Pins & Shorthand: Extensible IN1..IN16 and OUT1..OUT16 (default 2 in / 2 out, no underscores). Inside the expression, writing IN1 or OUT1 automatically means IN1.CV / OUT1.CV. Supports full Structured Text (IF...THEN...ELSE...ENDIF;, temporary variables, expt(), trig/log math).
  • Three 2:00 AM Gotchas:
    1. Outputs Default to GOOD (128): Unlike XFR, CALC does not auto-propagate input status! If IN2.ST (scale weight) goes BAD, OUT1.ST stays GOOD unless you explicitly write 'OUT1.ST' := 'IN2.ST';!
    2. Divide-by-Zero & Overflow: Dividing by zero or exceeding float limits (±3.40282e38) forces OUT.ST = BAD and sets Configuration Error in BLOCK_ERR (yellow ? On-Line!).
    3. ALGO_OPTS = AbortOnReadErrors: When enabled, if an external reference read fails, CALC aborts that scan rather than computing garbage from a stale value.

FB-3. CND — Condition Block (e.g., CND1..5, CND_VLV_HEALTH • FBR pp. 413–415)

  • Pins & Expression Rule: OUT_D output pin ONLY (zero input pins!). Operands are referenced inside a single-line expression; assignment := is illegal (CONFIG p. 62).
  • Built-In On-Delay Timer (TIME_DURATION): OUT_D and PRE_OUT_D set True (1) only after the expression stays continuously True for longer than TIME_DURATION seconds (e.g., 10 s on CND5 valve mismatch, 8 s on CND_ALIGN_ALM). If the condition flickers False for even 1 scan, the timer resets to zero!
  • 2:00 AM Plant Gotcha (DISABLE vs. PRE_OUT_D): Engineers sometimes bypass a nuisance CND block by setting DISABLE = True. That holds OUT_D = False, yet PRE_OUT_D still evaluates and turns True! Always check DISABLE and PRE_OUT_D if a condition looks True in the Expression Tree while OUT_D stays stuck at 0! Also, any unresolved reference sets OUT_D.ST = Bad: Configuration Error and blocks the expression from ever becoming True.

FB-4. ACT — Action Block (e.g., ACT1..2, ACT_PMP_GATE, ACT_FORCE_CLOSE • FBR pp. 400–401)

  • Pins & Execution: IN_D input pin ONLY (zero output pins!). Requires := to write directly to external/internal paths. Executes every single scan while IN_D = True (1) (not just once on a rising edge!); when IN_D goes False, the target keeps the last value written.
  • 2:00 AM Plant Gotcha (Status Is IGNORED!): Per FBR p. 401: "The status of IN_D does not impact the evaluation of the expression. The expression is evaluated whenever IN_D is True (1)." Even if IN_D has a Red ✕ (BAD status), if its .CV is 1, ACT still fires every scan! Never rely on ACT to reject a Bad input—guard .ST >= GOOD upstream in CND or CALC!

FB-5. DC — Device Control Block (DC1 inside every Valve/Motor CM • FBR pp. 417–427)

  • Modes (The #1 Discrete Trap): Supports ONLY AUTO (operator faceplate) and CAS (copies CAS_IN_D) as selectable target modes — NO MAN mode! Actual mode drops automatically to LO (Local Override) whenever TRK_IN_D = True, SHUTDOWN_D = True, INTERLOCK_D = False (interlock enabled), PERMISSIVE_D = False (while passive), or DC_STATE = Locked.
  • Built-In Confirm Timers & FAIL Codes: Built-in timers (CFM_PASS_TIME, CFM_ACT1_TIME, CFM_ACT2_TIME, CRACK_TIME, DELAY_TIME, TRIP_TIME) compare DC_STATE against field feedback FV_D. On timeout, DC writes a non-zero integer into FAIL (e.g., 1 = Passive Confirm Time) and sets FAIL_ACTIVE = True.
  • Hardware Personality (DEVICE_OPTS, FBR p. 422):
    • Pneumatic Valve: Keeps OUT_D energized even in Failed Active 1 so spring-return air valves don't hammer.
    • Motor: With Trip / Reset Required enabled, drops OUT_D straight back to Passive (de-energized) on trip or confirm failure.
    • Motorized Valve (MOV): With Passive when Confirmed enabled, de-energizes the drive coil once the limit switch confirms travel complete.

FB-6. AI — Analog Input Block (AI1 inside CM_TANK_WT & CM_HDR_PT • FBR pp. 92–99)

  • Signal Pipeline: Hardware I/O (IO_IN / CHANNEL) → FIELD_VAL (%) → L_TYPE scaling (Direct, Indirect, Indirect Square Root using OUT_SCALE) → LOW_CUT (zero-clamps tiny noise below threshold) → PV_FTIME (first-order filter time constant in seconds for a 63% step change; 0 = raw unfiltered) → PV → OUT (value + status).
  • Modes: Supports OOS, MAN (operator can manually type a fixed OUT value!), and AUTO (normal live sensor reading), plus IMan actual. Notice the contrast: AI HAS MAN mode, whereas discrete DC does NOT!
  • 2:00 AM Plant Gotchas:
    1. Raw Channel Bad Limits: If the field signal goes outside -20.12% to 116.6% (e.g., broken 4–20 mA wire at 0 mA = -25%), the I/O card automatically flags OUT.ST = BAD (Red ✕), tripping EM_TANK_CHARGE's CND2 interlock!
    2. Left-On SIMULATE Trap: Turning on SIMULATE lets an engineer inject fake tank weight during testing—and sets Simulate Active in BLOCK_ERR (showing a yellow highlighted ? On-Line!). Always look for yellow ? if a tank weight refuses to move during a live run!

Detailed Engineering Answer Key

1. A dashed wire is a feedback wire (source block executes after destination block, CONFIG p. 368). Numbering CND3 (#1) before CALC1 (#2) makes CND3 evaluate last scan's stale weight, adding one full scan period of unmeasured liquid flow before closing.

2. Only Pattern 1 (SFC) steps through time; Patterns 2, 3, and 4 solve continuously on every Scan even in Idle.

3. Discrete DC blocks only support AUTO (operator faceplate control) and CAS (upstream EM control) as target modes (FBR p. 427), plus LO on interlocks. If an operator leaves DC1 in AUTO or an interlock forces LO, MODE.ACTUAL is not CAS even if an earlier action wrote MODE.TARGET := CAS.

4. = GOOD only matches GoodNonCascade (128..191) and misses GoodCascade (192..255)—>= GOOD catches all Good statuses (CONFIG p. 81). Inside CALC1, outputs default to GOOD unless you write 'OUT1.ST' := 'IN2.ST';.

5. 800 kg gross (200 kg overfill!) — overwriting START_WT.CV := 300 erases the 200 kg already added and adds another full 500 kg on top of 300 kg.

6. CND has OUT_D only (zero input pins; reads operands inside its expression); ACT has IN_D only (zero output pins; writes directly via := every scan while IN_D = True).

7. An Items × States table (module-level Write & Readback parameter paths per item, 7016 p. 140—no SFCs!), driven by A_COMMAND and confirmed when A_PV updates from Idle (255) to the requested state.

8. Check the Items | States table (Tab 1) and CND_PATH_OK (Tab 2): an opposing valve (like Tank B's CM_HDR_XV102) is failing to prove PV.CV = CLOSED (or left in AUTO), holding CND_PATH_OK = False to prevent cross-contamination!

9. Discrete State-Driven EMs skip XFR/CALC analog math (Pattern 3), folding MODE.TARGET writes straight into table rows alongside Pattern 1 (state column select) and Pattern 4 (Write + Readback → A_PV). Only Pattern 2 (every-Scan health watchdogs and safe-close interlocks) stays on the FBD sheet.

10. Leaving BULK_CMD and DRIBBLE_CMD unchecked ((not written)) lets Auto Mode hand both valves back to operator faceplate control (MODE.TARGET := AUTO) without moving or slamming the valves—and DeltaV skips readback checks on unchecked cells so A_PV confirms Auto Mode immediately!

11. XFR sets OUT.ST to the worse status of the selected input AND SELECTOR (FBR p. 454), so a Bad SELECTOR forces OUT.ST = Bad! BAL_TIME (seconds) linearly ramps OUT from the old input to the newly selected input (0 = instant snap).

12. On CND, either DISABLE = True is bypassing OUT_D (check PRE_OUT_D, which still reads True!) or TIME_DURATION hasn't finished counting (FBR p. 414). On ACT, DeltaV completely ignores IN_D.ST—it fires every scan whenever IN_D.CV = 1 regardless of Bad status (FBR p. 401)!

13. Follow the gray dotted BKCAL_IN wire downstream to AO1: AO1 is out of CAS (in MAN or OOS) and is sending its current valve position + Not Invited (or Bad: OOS) backwards on BKCAL_OUT so PID1 tracks bumplessly in IMan!

14. Not Invited ripples backwards up both gray dotted BKCAL wires: both Slave PID_FIC and Master PID_TIC drop to IMan and track current valve/flow values, so returning AO_VLV to CAS is 100% bumpless with zero windup.

15. CTLSL provides individual BKCAL_SEL1..3 back-calculation wires back to every upstream PID so unselected PIDs stay windup-free (FBR p. 186). If any connected SEL_1..3 input goes Bad while in Auto, CTLSL automatically sheds its actual mode to Man (FBR p. 187).

16. Wire the trip into PID1/TRK_IN_D with TRK_VAL = 0.0% and enable both Track Enable and Track in Manual in CONTROL_OPTS (forcing MODE.ACTUAL = LO — FBR p. 234). CONTROL_OPTS can only be changed while the PID is in OOS mode!
